# Наплечники WoW Forever: разбор размера и привязки

Источник истины — исходники wow.export **v0.2.19** (та же версия, что указана в `asset.generator` всех трёх GLB) и определения DB2 из WoWDBDefs.

## 1. Что видно по приложенным данным

**Какой это предмет.** В GLB нет метаданных Item ID или DisplayID. Имя левого файла содержит FileDataID **7751193** (`shoulder_armor_skybornec60_d_01_l`). У правого файла FileDataID в имени нет. Цепочку ItemID → ItemDisplayInfo → ComponentModelFileData по приложенным файлам не восстановить: таблиц DB2 нет, а wago.tools и wow.tools из этой среды недоступны. Item ID можно надёжно получить из OBJ-эталона (п. 3): wow.export называет группу `Shoulder (L)_Item<ItemID>_0`.

**Масштаб: в данных он уже игровой, коэффициент не нужен.**
- wow.export ставит наплечник так: `M2RendererGL.getAttachmentTransform` → `model_matrix × bone_matrix × T(M2Attachment.position)`. Это только перенос, масштаба нет.
- В DB2 (ItemDisplayInfo, ComponentModelFileData, ChrRaces, ChrModel) нет поля масштаба наплечников.
- Скин предмета в GLB не меняет размер: одна кость `bone_0`, её узел равен `T(pivot)`, inverseBindMatrix равна `T(−pivot)`, вес 1 у всех вершин. В итоге преобразование тождественное.
- Значит, вершины GLB предмета уже в масштабе 1:1 с моделью персонажа, как в игре.

**Настоящая ошибка — положение, а не размер.**
- `attachShoulderAssets` вешал меш прямо в pivot `bone_ShoulderL` = (0.009, 1.591, −0.052). Это основание ключицы почти у позвоночника, без смещения точки крепления (M2 attachment 6 ShoulderLeft / 5 ShoulderRight).
  - Левый наплечник по оси z занимает [−0.396; +0.096] относительно своего начала координат. При такой привязке он попадает в [−0.448; +0.044], то есть заходит за осевую линию тела. Правый — зеркально, и оба перекрываются у шеи.
  - Для сравнения: сустав руки `bone_ArmL` на z = −0.163, торс на высоте 1.55–1.65 шириной ±0.255.
  - Предмет сдвинут к центру примерно на 0.11, поэтому на скриншоте он кажется крупнее.
- `attachDetachedShoulders` переносил меш на мировую матрицу `bone_Root` (+1.177 по Y). Это тоже подбор на глаз. GLB-экспорт wow.export пишет такие меши в координатах предмета (`get_equipment_geometry(false)`, `attachment_bone` не передаётся), так что правильный перенос — только `T(attachment.position)`.
- Модель персонажа выгружена в bind-позе (T-поза, без анимаций), а в игре персонаж стоит в анимации Stand. Влияние Stand на кость плеча видно только при экспорте с анимацией.

## 2. Что исправлено (`src/`)

- `deriveShoulderAttachments(objText, { L: glb, R: glb })` вычисляет точку крепления по эталону:
  1. Берёт группы `Shoulder (L/R)_Item…` из OBJ, выгруженного wow.export.
  2. Сопоставляет их вершины с вершинами GLB предмета. Совпадение проверяется по количеству и по UV.
  3. Подбирает аффинное преобразование методом наименьших квадратов.
  4. Принимает результат, только если это чистый перенос (масштаб 1, без поворота, RMS < 1e-3). Если эталон масштабирован или выгружен в позе, функция выдаёт ошибку с измеренным масштабом, а не подставляет его.
- `attachShoulderAssets(body, [{ side, file, attachment }])` требует `attachment.position` и ставит меш под `bone_Shoulder{L|R}` с матрицей `inv(bone_world) × model_world × T(position)`. Размер предмета не меняется (линейная часть — единичная), и меш следует за костью плеча. Без подтверждённых данных функция выдаёт ошибку.
- `attachDetachedShoulders(file, attachments)` работает по той же формуле. Без данных ничего не двигает и возвращает `missing: ['L','R']`.
- `wf-armory-shoulder-fix.js` (браузерный шим) повторяет ту же логику.
- Тесты: 11 из 11 проходят, включая реальные GLB из архива. Проверяется, что пересчитанное смещение совпадает с заданным до 1e-5 и что масштаб равен 1.

`wf-wow-model-viewer.js` и Release не изменялись.

## 3. Что нужно выгрузить из wow.export

Точка крепления наплечника (M2 attachment 5/6) — свойство модели персонажа, а не предмета. Поэтому подходит **любой наплечник** из списка wow.export: Skyborne в списке может не быть, если в загруженном клиенте нет этого предмета в ItemSparse.

1. **Characters**: `scourgefemale_hd`, тот же облик. Надеть любой наплечник из списка.
   - Анимация: **No Animation**.
   - Модель в превью не вращать.
   - Галочка **Apply pose** включена (по умолчанию).
2. **Export → OBJ**. Нужен только `.obj`.
3. Не меняя ничего, **Export → GLB** того же персонажа. В нём wow.export кладёт наплечники в их собственных координатах — это и есть данные для сравнения с OBJ.
4. По желанию, для проверки кости крепления: сырые `scourgefemale_hd.m2` и `.skel` (Export → Raw). Сейчас, как и раньше, принято, что ID 5/6 крепятся к `bone_ShoulderR/L`.

GLB персонажа без OBJ не поможет: в версии 0.2.19 GLB-экспорт пишет наплечники без точки крепления (см. п. 1).

## 4. Результат по присланному OBJ (Item 271754)

- **Модели те же.** Вершины групп `Shoulder (L/R)_Item271754_0` совпали с вершинами приложенных GLB Skyborne (626 и 625 вершин, RMS 3.5·10⁻⁸ после подбора преобразования).
- **Игровой масштаб наплечников этой нежити — 0.65.** Преобразование «GLB предмета → OBJ» на обеих сторонах — равномерный масштаб 0.6500 (сингулярные числа 0.649995–0.649999) плюс поворот. Без этого масштаба наплечники в приложении в 1/0.65 ≈ **1.54 раза** больше игровых.
- **Откуда масштаб.** OBJ выгружен с анимацией: тело в стойке, руки опущены, высота 1.83 вместо 2.15 в T-позе. При «No Animation» матрицы костей в wow.export единичные, поэтому 0.65 — из анимационных данных скелета.
- **К какой кости крепится наплечник.** В скелете есть отдельные корневые кости `bone_$SHL` и `bone_$SHR` с опорной точкой в начале координат. Это служебные кости точек крепления: их анимация может масштабировать наплечник, не трогая руку. Масштаб 0.65 у `bone_ShoulderL/R` уменьшил бы и руку. Поэтому, скорее всего, attachment 5/6 привязан к `$SHR/$SHL`. В T-позе эти кости стоят в начале координат — отсюда и «наплечники в начале сцены» в старом GLB. Окончательно это подтвердят анимации или сырые `.m2`/`.skel`.
- **Особенность wow.export.** В OBJ надетые предметы повёрнуты на угол модели в окне просмотра (`getAttachmentTransform` умножает на `model_matrix`), а тело — нет. Поворот около −95°, поэтому в этом OBJ левый наплечник оказался спереди, правый сзади. Функция теперь распознаёт поворот вокруг вертикали в OBJ без анимации и убирает его.
- Этот OBJ отклонён как эталон точки крепления: в нём есть анимация. Масштаб и поворот из одного кадра Stand без данных анимации не разделить на «кость» и «точку крепления».

### Что нужно дальше
1. **OBJ с No Animation** (тот же персонаж и наплечники) — даст точку крепления в позе покоя.
2. **GLB с галочкой Export animations** — даст анимацию Stand, где у `$SHL/$SHR` должен быть масштаб 0.65. Если приложение будет проигрывать Stand, а наплечники будут прикреплены к `$SHL/$SHR`, размер и положение совпадут с игрой без ручных коэффициентов.

## Использование

```js
const att = await WFArmoryImport.deriveShoulderAttachments(objText, { character: characterWithShouldersGlb });
// или { L: leftItemGlb, R: rightItemGlb }, если OBJ выгружен именно с этими моделями
// att.L = { itemId, position: [x, y, z], scale: 1, rms, vertexCount }
const { blob } = await WFArmoryImport.attachShoulderAssets(bodyGlb, [
  { side: 'L', file: leftGlb, attachment: att.L },
  { side: 'R', file: rightGlb, attachment: att.R }
]);
```

`att` можно сохранить как подтверждённую трансформацию для этой пары «модель персонажа + DisplayID» и не пересчитывать.

Игровые GLB и скриншот в репозиторий не добавлены (`.gitignore`): репозиторий публичный. Тест на реальных данных запускается, если положить их в `data/`.
